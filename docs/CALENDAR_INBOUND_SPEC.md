# Personal calendar → SkyRunners: the spec

Status: **specified, not built.** Written 2026-08-14 alongside the outbound feed,
which IS built and live (`docs/CONNECT_YOUR_CALENDAR.md`).

The ask, in Anish's words: *"when someone makes an event on say their apple
calendar, it should automatically add an entry on the skyrunners calendar."*

This document exists because that is a bigger job than it sounds, needs
credentials nobody in a coding session can obtain, and has one hard limit worth
knowing before anybody starts.

---

## Read this first: Apple is not possible, and never will be

Not "hard". Not "later". There is no mechanism.

- **Apple publishes no calendar API.** There is no OAuth, no REST endpoint, no
  webhook. iCloud Calendar is reachable only over **CalDAV**, and CalDAV
  authentication for third parties means an **app-specific password**.
- An app-specific password is a credential granting **full read and write access
  to the member's entire personal calendar**, generated by hand at appleid.apple.com
  and pasted into a student club website. It cannot be scoped to one calendar, and
  it cannot be scoped to read-only.

**Do not build that.** The outbound half already gives Apple users everything
except inbound, and asking thirty undergraduates to hand over an Apple credential
to gain "I can create a club event from my phone's calendar" is not a trade this
app should offer. It is also the single most likely thing in this repo to end up in
a screenshot in a group chat.

So inbound is **Google and Microsoft only**, and the member docs must say so
plainly rather than letting Apple users discover it by it not working.

---

## The filter: a dedicated calendar, chosen 2026-08-14

Taken literally, "an event I make in my calendar appears on the club calendar"
would put dentist appointments, lectures and dates on a page thirty people read.
Anish picked the version that cannot leak:

> The member creates one calendar called **SkyRunners** in Google or Outlook. Only
> events in that calendar sync. Putting an event there IS the opt-in.

Why this beat the alternatives:

| Option | Why not |
|---|---|
| Keyword in the title, e.g. `[SR] Spar layup` | No setup, but it is a rule to remember every single time, and a forgotten prefix fails **silently** — the member believes the club can see it |
| Everything, member approves each one on the site | Nothing leaks, but it creates a queue to keep clearing. This app already rejected the quarterly re-enrollment sweep for being exactly that kind of recurring chore |
| A dedicated calendar | **One decision, once.** Nothing personal can leak even in principle, and there is no per-event step to forget |

One consequence to design for: a member will put something in the wrong calendar
and wonder why it didn't sync. The setup page should say what the calendar must be
called, and the connection panel should show **which calendar** is connected and
when it last imported, so "nothing has come across" is diagnosable without asking
anybody.

## What Kelvin has to do before a line of this works

This is the blocker, and it is the reason the outbound feed was built first: the
feed needs no credentials at all, and none of this works without four.

### Google

1. Google Cloud Console → new project (or the club's existing one).
2. Enable the **Google Calendar API**.
3. OAuth consent screen: **External**, scoped to the club. Add
   `anish25@stanford.edu` and Kelvin as test users until it is verified.
4. Create an **OAuth 2.0 Client ID**, type *Web application*.
5. Authorised redirect URI — exactly this, no trailing slash:
   `https://skyrunners-app.vercel.app/api/calendar/connect/google/callback`
6. Scope: **`https://www.googleapis.com/auth/calendar.events.readonly`**.

   Read-only, and only events. Not `calendar`, not `calendar.events` — the
   outbound half is already handled by the ICS feed, so write access buys nothing
   and would put the club's app one bug away from deleting somebody's calendar.
   Google's consent screen names the scope, and members will read it.

7. Vercel env vars: `GOOGLE_CALENDAR_CLIENT_ID`,
   `GOOGLE_CALENDAR_CLIENT_SECRET`.

### Microsoft

1. Azure Portal → Microsoft Entra ID → **App registrations** → New.
2. Supported account types: **personal + work/school**, so both an
   `@stanford.edu` account and a personal Outlook work.
3. Redirect URI (Web):
   `https://skyrunners-app.vercel.app/api/calendar/connect/microsoft/callback`
4. API permissions → Microsoft Graph → **delegated** → **`Calendars.Read`**.
   Delegated, never Application: Application permission would grant the club's
   server access to *every* calendar in the tenant, which is a wildly
   disproportionate thing to hold.
5. Certificates & secrets → new client secret. **Note the expiry** — Azure
   secrets expire, 24 months maximum, and when it does every member's import stops
   at once with no symptom on the site. Put the date somewhere it will be seen.
6. Vercel env vars: `MICROSOFT_CALENDAR_CLIENT_ID`,
   `MICROSOFT_CALENDAR_CLIENT_SECRET`.

**Until all of these exist, the feature must be inert rather than half-working** —
the same rule the MCP server follows when `SUPABASE_SERVICE_ROLE_KEY` is missing:
say so in one sentence, do not partly function.

## Schema sketch

```sql
create table calendar_connections (
  id              uuid primary key default gen_random_uuid(),
  member_id       uuid not null references profiles (id) on delete cascade,
  provider        text not null check (provider in ('google', 'microsoft')),

  -- The provider's id for the ONE calendar being watched. Null until the member
  -- has picked it, which is a separate step from authorising.
  calendar_id     text,
  calendar_name   text,

  -- ENCRYPTED AT REST, not merely hashed. Unlike every other secret in this
  -- schema these have to be USED, so a one-way hash is not an option — which
  -- makes this the most sensitive table in the database and the reason it must
  -- never be selected into the page snapshot in `lib/store/mapping.ts`.
  access_token    text not null,
  refresh_token   text not null,
  expires_at      timestamptz not null,

  -- Incremental sync. Google gives a syncToken, Graph gives a deltaLink; both
  -- mean "changes since last time" and both can be invalidated by the provider,
  -- which must trigger a full resync rather than an error.
  sync_cursor     text,
  last_synced_at  timestamptz,
  last_error      text,

  unique (member_id, provider)
);
```

`events` needs two columns so an imported event is recognisable on the way back
in and never duplicated:

```sql
alter table events
  add column source           text not null default 'skyrunners',
  add column external_id       text,
  add column external_etag     text;

create unique index events_external_idx
  on events (source, external_id) where external_id is not null;
```

That unique index is the whole duplicate-prevention mechanism. Without it, every
poll re-creates every event.

## Sync mechanics, and the constraint that shapes them

**Vercel Hobby allows at most one cron run per day, per job, and it rejects the
entire deployment if you break that rule.** That has already cost this project
four failed deploys — see `docs/HANDOFF.md`. Do not touch `vercel.json`'s
schedules to make polling faster.

So a daily cron gives up-to-24-hour staleness, which is too slow for "I made it on
my phone and it should be on the club calendar". Two real options:

1. **Push notifications** (recommended). Google Calendar supports watch channels;
   Graph supports subscriptions. Both POST to an endpoint when something changes,
   which makes imports near-instant with no cron at all. Both need renewing —
   Google channels expire in about a week, Graph subscriptions in about three days
   — and that renewal is a legitimate use of the existing daily cron.
2. **Sync on sight**: import when the member loads `/calendar`. No infrastructure,
   and self-limiting, but it means an event only crosses over once its owner
   visits the site, which is the behaviour this feature exists to remove.

Recommended: **(1) for freshness, with (2) as the fallback and the renewal riding
on the daily cron.**

## Rules the implementation must hold

1. **An imported event is clearly marked as imported.** `source = 'google'`, shown
   on the calendar UI. A club-wide page must not imply the club scheduled
   something one member put in their own calendar.
2. **Never write back what came in.** An imported event is a mirror. Editing it on
   the website and pushing that to the member's calendar needs write scope, which
   step 6 above deliberately does not request.
3. **Deleting it in the personal calendar deletes it here.** The alternative —
   an orphan the member cannot remove without signing in — is worse than a
   disappearing event.
4. **No attendees are inferred.** The person who created it is the organiser and
   the only attendee. Anish flagged this himself: *"Adding other people may be
   hard through the apple calendar, but it should be on the website so everyone
   can see that it's happening."* Exactly right — the value is visibility, and
   membership stays an RSVP on the site.
5. **Revoking is one press, and revokes at the provider too.** Deleting the row is
   not enough; call Google's revoke endpoint so the grant disappears from the
   member's own Google account page.
6. **`calendar_connections` never enters the page snapshot.** Follow
   `lib/mcp/store.ts` and `lib/calendar/store.ts`: credentials go straight to
   Postgres and never through `lib/store/*`, or every project page would carry
   thirty members' calendar tokens in memory.
7. **The connection panel shows the last error.** A refresh token dies silently.
   Without a visible "last import failed", the symptom is a member insisting they
   made an event weeks ago.

## Rough shape of the work

| Piece | Notes |
|---|---|
| `lib/calendar/oauth.ts` | Authorise URL, code exchange, refresh. Pure where possible |
| `app/api/calendar/connect/[provider]/route.ts` | Start the flow. `state` must be a signed nonce, or it is a CSRF hole |
| `.../callback/route.ts` | Exchange, store, then send the member to pick their calendar |
| `lib/calendar/import.ts` | Provider payload → `ClubEvent`. Pure, and where the tests go |
| `app/api/calendar/webhook/[provider]/route.ts` | Push notifications. Needs the middleware exclusion, like `api/calendar` |
| Migration | The two blocks above |
| Settings UI | Connect / pick calendar / show last import / disconnect |
| Docs | Add the Google + Outlook steps, and state plainly that Apple is outbound-only |

The pure modules — `import.ts` especially — are where the value is. Provider
payloads are fiddly (all-day events are date-only, recurrence is a nightmare,
cancellations arrive as tombstones), and every one of those is testable without a
network if the parsing is separated from the fetching.

**Recurring events deserve their own decision before anybody starts.** A weekly
lab session is one event with a recurrence rule, and expanding it into fifty-two
rows would flood the club calendar — which is exactly the noise the project Gantt
was just changed to avoid. Recommended: import the series as a single event and
show the rule, or skip recurring events in v1 and say so.
